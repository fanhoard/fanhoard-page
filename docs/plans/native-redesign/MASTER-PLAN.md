# แผนหลัก FanHoard Native Redesign

- **System Described**: แผนหลักการออกแบบ FanHoard ใหม่ให้เป็นสไตล์แอปเนทีฟ (Emoji-first บนโครง Soft Paper)
- **Entry File**: `docs/plans/native-redesign/MASTER-PLAN.md`
- **Dependencies**: `assets/css/tokens.css`, `assets/css/base.css`, `assets/js/home.js`, `assets/db/con-data/`
- **Verification**: `npm run build` | `npx vitest run tests/popup tests/stability-defects.test.ts tests/scroll-lock-core.test.ts tests/e2e-dom`

กฎของไฟล์นี้: ห้ามมีวิธีทำ ห้ามมีโค้ด ห้ามมีค่าตั้งค่า มีเพียง ขั้น เป้าหมาย ผลลัพธ์ที่ตรวจได้ สถานะ และลิงก์ไปไฟล์ลึก
รายละเอียดของแต่ละขั้นอยู่ใน `docs/plans/native-redesign/steps/` เมื่อแผนเปลี่ยน ให้แก้ไฟล์ลึกของขั้นนั้นกับแถวเดียวในตารางนี้ ไม่ต้องรื้อทั้งชุด

## 1. หมุดหมายเดียว

**เว็บ FanHoard ทั้ง 14 หน้ามีหน้าตาและการใช้งานแบบแอปเนทีฟสมัยใหม่ มีตัวตนของตัวเอง โดยฟังก์ชัน ลิงก์ และข้อมูลเดิมครบทุกอย่าง**

จะเรียกว่าสำเร็จเมื่อผ่านเกณฑ์ระดับระบบทั้ง 5 ข้อนี้บนเว็บจริง ไม่ใช่ในเครื่องผู้พัฒนา:

| ข้อ | เกณฑ์ระดับระบบ (ตรวจได้) |
|---|---|
| 1 | ทั้ง 14 หน้าใช้องค์ประกอบกลางชุดเดียวกัน ไม่มีหน้าใดยังใช้หน้าตาเก่าปะปน |
| 2 | ทุกหน้าไม่มีเลื่อนแนวนอนที่ 390 และ 1440 พิกเซล และไม่มี error ของหน้าบนเว็บจริง |
| 3 | ฟังก์ชันเดิมทำงานบน DOM จริง: ค้นหา คัดลอก ตั้งค่า เปลี่ยนภาษา ป๊อปอัป และ scroll-lock ปลดเมื่อกด Escape |
| 4 | ข้อความทุกจุดผ่านเกณฑ์ contrast AA ในธีมสว่าง และธีมมืดอ่านออกทุกจุด |
| 5 | ทุกรุ่นที่ปล่อยมีโน้ตรุ่นสองภาษาและผ่านการตรวจบนเว็บจริงก่อนไปขั้นถัดไป |

## 2. ทิศทางที่ล็อกแล้ว (Master ตัดสิน 17 ต.ค. 2026)

- ทำองค์ประกอบกลางก่อน แล้วรื้อโครงทีละกลุ่มหน้า ฟังก์ชันและ URL เดิมครบ
- ตัวตน: Emoji-first บนโครง Soft Paper UI เงียบ อีโมจิเป็นพระเอก
- สีแบรนด์: คงเขียว แต่ปรับสัดส่วนการใช้ให้ผสมกับสีรองได้อย่างลงตัว
- ธีมสว่างทำให้สมบูรณ์ก่อน ธีมมืดให้ใช้งานได้ปลอดภัยตามเดิม
- อีโมจิใช้ของอุปกรณ์ตามเดิม ไม่ฝังชุดอีโมจิเอง
- ตัวอักษรคง system-ui แต่จัดน้ำหนัก ขนาด และระยะเป็นระบบ ไม่เพิ่มไฟล์ฟอนต์
- Home สลับหมวดด้วยแถบแคปซูล แสดงทีละหมวด ไม่เลื่อนยาวต่อเนื่อง
- ไม่ทำสีตามหมวดในรอบนี้ (ดูหัวข้อ 4)
- แถบเมนูล่างคงตำแหน่งและพฤติกรรม hover/active/focus เดิม
- ทุกขั้นเป็นรุ่นย่อยหนึ่งชุด 1 patch ต่อ 1 delivery ตรวจบนเว็บจริงก่อนไปต่อ
- ปล่อยขึ้นสาขา develop เท่านั้น

## 5. กติกาถ้าเวลาไม่พอ

- S5 เป็นขั้นที่เลื่อนได้ เพราะ 8 หน้านี้ใช้งานได้เหมือนเดิมอยู่แล้วโดยไม่ต้องมีขั้นนี้
- S1 เป็นฐานของทุกขั้น เลื่อนไม่ได้
- ถ้าขั้นใดไม่ผ่านการตรวจบนเว็บจริง ต้องแก้ให้ผ่านก่อนไปขั้นถัดไป ห้ามข้าม
- การตัดสินว่าอะไรเลื่อนเป็นของ Master เสมอ ผู้พัฒนาไม่เลื่อนเอง

## 6. สิ่งที่ยังไม่ทราบ (ต้องวัดหรือตรวจก่อนอ้างเป็นข้อเท็จจริง)

- ภาพตัวอย่างจาก Instagram และ Threads ที่ Master จะส่งเพิ่ม อาจปรับทิศทางที่ล็อกไว้
- ผลกระทบของโครง Home แบบสลับหมวดต่อ SEO ตรวจแล้ว 17 ต.ค. 2026: การ์ดทั้งหมดถูก JS วาดจากไฟล์ข้อมูลอยู่แล้ว HTML ที่เสิร์ชเอนจินเห็นไม่มีเนื้อหาการ์ด การสลับหมวดจึงไม่ทำให้แย่ลงจากเดิม ส่วนเรื่องทำให้ดีขึ้นอยู่นอกขอบเขตรอบนี้
- เวลาที่ใช้จริงของแต่ละขั้น ยังไม่เคยวัด

## 7. ข้อจำกัดแพลตฟอร์ม

- โปรเจกต์เป็น HTML CSS JS ล้วน ไม่มีเฟรมเวิร์ก สร้างด้วยสคริปต์ build ของโปรเจกต์
- เว็บตั้ง CSP เข้ม ทุกการทดสอบต้องเสิร์ฟด้วย CSP เดียวกับเว็บจริง (dist/_headers)
- ไฟล์ที่ CI สร้างห้าม commit: version.json, releases/*, ตัวต่อท้ายแคชใน HTML
- ทุกรุ่นต้องอัปเดต assets/md/en/current.md และ assets/md/th/current.md
