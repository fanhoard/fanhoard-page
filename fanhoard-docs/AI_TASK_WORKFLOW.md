## 1. Five Core Principles

### 1.1 Comprehend Before Editing
Never begin editing source code before fully establishing:
- The exact user requirement and scope boundaries.
- How the target subsystem operates in live v3.0.0 code.
- Potential side effects on adjacent components and build validation scripts.

### 1.2 Ground All Decisions in Specs
Every architectural decision must rely on documented repository standards rather than assumptions:
- **Inviolable Rules**: [`AI_FORBIDDEN.md`](./AI_FORBIDDEN.md)
- **Code Standards**: [`AI_CODING_GUIDE.md`](./AI_CODING_GUIDE.md)
- **System Architecture**: [`00-System-Architecture.md`](./00-System-Architecture.md) and [`INDEX.md`](./INDEX.md)

### 1.3 Step-by-Step Execution
Decompose work into incremental steps. Complete, test, and verify one step before proceeding to the next.

### 1.4 Validate Before Delivery
Every task delivery must pass all checks in [`AI_REVIEW_CHECKLIST.md`](./AI_REVIEW_CHECKLIST.md) and local 4-layer release validation gates.

### 1.5 Explicit Reporting
Deliver structured reports specifying modified files, verified behavior, and remaining steps.

## Phase 1: Task Comprehension

### Step 1.1: Detailed Request Analysis
Read the user instructions completely:
1. Skim once for overall objectives.
2. Read carefully to extract technical constraints and acceptance criteria.
3. Formulate a 1-sentence mental or written summary of the deliverable.

### Step 1.2: Clarify Ambiguities
If a request contains ambiguous directives or missing details, state the ambiguity clearly or resolve it against repository code before proceeding.

### Step 1.3: Reference Documentation Review
Read documentation in the following sequence:
1. [`AI_FORBIDDEN.md`](./AI_FORBIDDEN.md) — System invariants and prohibited patterns.
2. [`AI_CODING_GUIDE.md`](./AI_CODING_GUIDE.md) — Code style, IIFE patterns, and DOM conventions.
3. [`00-System-Architecture.md`](./00-System-Architecture.md) — System-wide architecture and module contracts.
4. Target subsystem guide (e.g., `02-Search-System.md` for search changes).

### Step 1.4: Codebase Exploration
- Use `grep` to locate relevant functions, constants, and event listeners.
- Use file search to identify related stylesheets and module files.
- Inspect surrounding code to match existing implementation patterns.

### Step 1.5: Task Scope Summary
Formulate a concise task scope block before writing code:

```
Task: <One-sentence objective summary>
Scope: <Exact target files and modules>
Constraints: <Invariants, bypass counter rules, performance limits>
Approach: <Step-by-step implementation strategy>
```

## Phase 2: Planning & Impact Analysis

### Step 2.1: Subtask Decomposition
Break complex tasks into discrete, verifiable subtasks. Each subtask must produce a testable outcome and resolve a specific requirement.

### Step 2.2: Identify Target Files
Construct an explicit file modification list with rationale:

```
Target Files:
- assets/js/search-system/search-modules/engine.js — Implement fuzzy matching helper
- assets/js/search-system/search-modules/state.js — Add state fields for candidate score
- assets/css/search.css — Add styling for highlighted search matches
```

### Step 2.3: Cross-System Impact Assessment
Evaluate potential ripple effects across subsystems:
- **Search System Changes**: Affects `URE` virtual rendering and `Nav-Core` display overlay.
- **Language / i18n Changes**: Affects all UI modules listening for language events (`window.FvLang`).
- **ConData Changes**: Affects search indexing, category navigation, and homepage cards.
- **Release Notes / Versioning Changes**: Modify strictly `assets/md/{en,th}/current.md`. Do NOT edit files under `assets/md/{lang}/releases/` directly (these are generated by `scripts/update-version.js`).

### Step 2.4: SEO Impact Analysis
When modifying HTML structure, routing, or page rendering:
- **URL / Path Changes**: Require 301 redirect configuration, sitemap update, and canonical tags.
- **Meta Tag Changes**: Must be mirrored across all supported locales (`en`, `th`).
- **Rendering Changes**: Core content must remain present in static HTML for crawler indexing.

### Step 2.5: Test Plan Formulation
Define validation steps prior to editing code:
- Local verification commands (`node scripts/validate-release.js --staged`, `npm run test`).
- Console log inspection for errors or missing namespace dependencies.
- Multi-language verification (`en` and `th`).

## Phase 3: Execution

### Step 3.1: Sequential Subtask Implementation
Complete subtasks one at a time. Do not jump between unrelated subtasks or modify files outside defined scope.

### Step 3.2: Adhere to Coding Standards
Ensure all newly added or modified lines comply with [`AI_CODING_GUIDE.md`](./AI_CODING_GUIDE.md):
- IIFE module wrapper with `'use strict';`.
- 2-space indentation and mandatory semicolons.
- JSDoc documentation on exported methods.
- Strict XSS protection using `textContent` for user inputs.

### Step 3.3: Invariant Enforcement
Continuously cross-check changes against [`AI_FORBIDDEN.md`](./AI_FORBIDDEN.md):
- No ES module imports/exports in browser runtime scripts.
- No direct edits to generated release artifacts under `releases/`.
- No global state mutation outside declared subsystem namespaces.

### Step 3.4: Handling Unexpected Failures
If an unexpected error or test failure occurs:
1. Isolate the cause using local execution or focused logs.
2. Re-evaluate assumptions against live code.
3. Adjust implementation or refine planning steps before proceeding.

## Phase 4: Testing & Verification

### Step 4.1: Run AI Review Checklist
Execute all checks in [`AI_REVIEW_CHECKLIST.md`](./AI_REVIEW_CHECKLIST.md) to ensure quality compliance.

### Step 4.2: Automated & Manual Testing
Run local verification commands:

```bash
# Verify 4-layer release gate rules
node scripts/validate-release.js --staged

# Execute Vitest test suite
npm run test
```

Verification Checklist:
- [ ] Local build and validation commands exit with zero error code.
- [ ] Browser console reports zero unhandled errors or missing module warnings.
- [ ] Modified functionality behaves as specified.
- [ ] No regression introduced in existing features.
- [ ] Multi-locale output verified for both `en` and `th`.

### Step 4.3: Cross-System Regression Check
- Verify that dependent subsystems consuming updated APIs function without errors.
- Confirm that event dispatchers and listeners interact cleanly.

## Phase 4.5: Documentation Synchronization (Priority #1)

Documentation accuracy is a top priority in FanHoard. Code changes and documentation updates MUST remain synchronized within the same commit.

### Step 4.5.1: Identify Documentation Dependencies
Consult the documentation sync matrix in [`13-Documentation-Standard.md`](./13-Documentation-Standard.md):

| Code / System Change | Documentation Target |
| :--- | :--- |
| **Add/Remove Module** | Subsystem specification + `00-System-Architecture.md` |
| **Modify Public API** | Subsystem specification + `00-System-Architecture.md` |
| **Change Namespace** | `00-System-Architecture.md` + `AI_CODING_GUIDE.md` |
| **Modify Build / Release Logic** | `09-Deployment-Guide.md` + `release-policy.md` |
| **Add/Remove Content Type** | `10-Content-Guide.md` + `05-Content-Data-Service.md` |
| **Add/Remove Route or Page** | `00-System-Architecture.md` + `09-Deployment-Guide.md` |

### Step 4.5.2: Verification of Referenced Code Facts
Before committing documentation changes, verify that all cited function names, constants, line numbers, and file paths match live code.

### Step 4.5.3: Atomic Commit Rule
Stage code modifications and corresponding documentation files together in a single commit step.

```bash
# Correct atomic commit
git add assets/js/search-system/search-modules/engine.js fanhoard-docs/02-Search-System.md .release-bypass
git commit -m "feat(search): update candidate bucket index + update search docs"
```

## Anti-Patterns

### ❌ Anti-Pattern 1: Unplanned Code Editing
Editing source files without reading subsystem guides or conducting impact analysis leads to broken invariant checks and broken releases.

### ❌ Anti-Pattern 2: Non-Atomic Documentation
Pushing code changes without updating corresponding `fanhoard-docs/` specifications creates stale documentation and breaks system SSOT rules.

### ❌ Anti-Pattern 3: Editing Generated Artifacts Directly
Modifying files in `assets/md/{lang}/releases/` or `assets/json/version.json` directly violates release pipeline rules enforced by `scripts/validate-release.js`.

### ❌ Anti-Pattern 4: Silencing Errors
Catching and ignoring exceptions in async blocks prevents proper error recovery and hides critical runtime failures.

```
Phase 1: Task Comprehension ──► Read prompt 3x ──► Check AI_FORBIDDEN.md ──► Formulate Scope
Phase 2: Planning          ──► Decompose Subtasks ──► List Target Files ──► Assess Impact & SEO
Phase 3: Execution         ──► Sequential Edits ──► Enforce AI_CODING_GUIDE ──► Check Invariants
Phase 4: Verification        ──► Run AI_REVIEW_CHECKLIST ──► Run Local Gates ──► Test Both Languages
Phase 4.5: Doc Sync        ──► Update fanhoard-docs/ ──► Verify Specs vs Code ──► Atomic Commit
Phase 5: Delivery          ──► Present Summary Report ──► Detail Verified Gate Results
```
